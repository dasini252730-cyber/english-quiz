## 작업 범위

### 설계 선택지 (비용·복잡도 비교)

#### 선택지 1: 서버 스케줄 + 결과 테이블 (pg_cron)
**구현:**
- Edge Function: Batch API 제출 엔드포인트 (/batch-submit) 추가
- Supabase 스케줄 (pg_cron): 자정(Seoul) 마다 배치 결과 수거, 앱 DB에 저장
- 결과 테이블: 배치 ID, 상태(대기중/완료/실패), 결과 JSON, 생성일시

**장점:**
- 앱은 무조건 콘텐츠가 있으므로 폴링 불필요
- 비용: 50% 절감 (하루 2회 Batch, Messages API 대비 토큰당 0.5배)
- Batch API 특화: 대량 요청에 최적

**단점:**
- 서버 복잡도: pg_cron 설정, 결과 수거 로직, 실패 재시도
- Supabase 스케줄의 실행 보장 없음 (지연 가능, 100% 신뢰성 아님)
- 배치 만료(24h)까지 결과 미보유 위험
- 앱 버전 호환성: 결과 스키마 변경 시 중계 필요

#### 선택지 2: 앱 폴링 (ContentPrefetcher 확장)
**구현:**
- Edge Function: /batch-status 엔드포인트 (배치 ID의 상태 조회)
- ContentPrefetcher: 내일 콘텐츠 미생성 시 배치 ID로 폴링 시작 (1~5초 간격)
- 결과 캐시: 폴링 완료 후 앱 DB에 저장

**장점:**
- 서버 로직 최소: 단순 상태 조회만 필요
- 앱이 완전히 제어: 실패 시 앱이 즉시 인지

**단점:**
- 앱 배터리: 백그라운드 폴링으로 전력 소비
- 네트워크 재시도: Batch 준비 중(1~10분)에 폴링하면 쓸데없는 호출 증가
- 사용자 경험: 콘텐츠 도착 예측 불가 (대기 시간 불명확)
- 비용: 폴링 호출도 계산 필요 (체크 당 토큰 0 이지만 함수 호출 횟수 카운트)

#### 선택지 3: 하이브리드 (배치 제출 + 앱 폴링)
**구현:**
- Edge Function: /batch-submit (배치 제출 및 ID 반환)
- ContentPrefetcher: 배치 ID 저장 후, 다음 세션 시작 전에 결과 확인
- 실패 폴백: 폴링 타임아웃(>2h) 시 Messages API 직접 호출

**장점:**
- 비용: Batch 우선 (50% 할인), 실패 시 즉시 Messages API로 대체
- 신뢰성: 어느 경로든 콘텐츠 보장
- 세션마다 최대 1회 폴링 (배터리 영향 최소)

**단점:**
- 서버 중간 수준 복잡도
- 앱 내 상태 관리 증가 (배치 ID 저장, 폴링 타임아웃 정책)

### 기술 결정 사항

**비용 계산 (월 40회 호출 기준):**
- Messages API: 약 40~50만 원 (Sonnet 5 기준, 평균 2000 input + 1500 output 토큰)
- Batch API: 약 20~25만 원 (0.5배) + 선택지에 따라:
  - pg_cron: 서버 CPU 비용 무시할 수준
  - 폴링: +데이터 전송 비용 (negligible)

**구현 우선순위:**
1. 실 배포 전: ContentPrefetcher의 Messages API → Batch 전환 설계
2. 결정 필요:
   - 서버 복잡도 vs 비용 절감 트레이드오프
   - Supabase pg_cron 신뢰성 허용 수준

### 선택지 3 (하이브리드) 스코프
1. 선택지 1 + 선택지 2 통합
2. 타임아웃 정책 정의
