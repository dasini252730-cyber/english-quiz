# 013 학습 난이도 자동 조절

## 목적
진단 결과를 출발점으로 학습 성과에 맞는 후속 콘텐츠 난이도를 제공한다.

## 작업 범위
- 초기 난이도를 진단 결과에서 가져온다.
- 퀴즈 정답률, 최근 학습 성과, 저장 표현 빈도와 콘텐츠 표현 난이도를 사용한다.
- 난이도 조절은 일반 프로그램 로직으로 수행하고 다음 생성 요청에 반영한다.
- 사용자 직접 CEFR 선택 기능은 제공하지 않는다.

## 완료 기준
- 조정 기준과 상·하향 경계가 설명 가능하고 테스트 가능하다.
- 콘텐츠 생성 입력에 최신 난이도가 전달된다.
- 급격한 난이도 진동을 방지하는 규칙이 있다.

## 2026-09-22 구현 (006 없이 가능한 범위)

AI 키가 막혀 있어도 이 작업은 대부분 진행할 수 있어 먼저 구현했다. 난이도는 순수 계산이고, 생성 요청에 난이도를 넘기는 통로는 006 준비 코드에 이미 있었다.

### 확정된 구현 결정 (메인)
- 난이도 척도는 `AssessmentLevel.storedValue` 와 같은 1~3 이다. 별도 CEFR 값을 만들지 않는다.
- 판단 창은 **최근 3세션**이다. 한 세션만 보고 움직이면 그날 컨디션에 휘둘린다.
- 정답률은 창 전체를 **pooled** 로 계산한다(정답 합 ÷ 문항 합). 세션별 비율을 평균내면 3문항짜리 날이 20문항짜리 날과 같은 무게를 갖는다.
- **상향**: 정답률 85% 이상 **그리고** 세션당 평균 신규 저장 2개 이하.
- **하향**: 정답률 50% 미만 **또는** 세션당 평균 신규 저장 12개 이상.
- 하향이 상향보다 우선한다. 학습자를 막힌 채로 두는 쪽이 늦게 올려 주는 쪽보다 나쁘다.
- 진동 방지는 두 겹이다. 한 번에 **±1단계**만 움직이고, 움직인 뒤에는 **창이 다시 찰 때까지**(3세션) 움직이지 않는다.
- 퀴즈가 비어 있던 창(오늘 복습할 표현이 없던 날들)은 난이도를 움직이지 않는다. 저장 빈도만으로 판단하면 근거가 부족하다.
- 요구사항 8절의 네 번째 입력인 "콘텐츠 내 표현 난이도"는 측정 수단이 없어 직접 쓰지 않는다. 표현에 점수를 매기는 곳이 없고, 생성물의 수준은 이 함수가 돌려주는 값이 정한다. **저장 표현 빈도가 그 대리 지표**다. 뜻을 많이 찾아봐야 했던 지문은 어려웠던 것이고, 거의 안 찾은 지문은 쉬웠던 것이다.

### 만든 것
- `domain/difficulty/DifficultyPolicy.kt` — 순수 Kotlin object. 시계·저장소·AI 를 읽지 않고 입력만으로 결정된다. `StreakPolicy` / `ReviewPolicy` / `QuizBuilder` 와 같은 패턴이다.
- `domain/difficulty/DifficultyPolicyTest.kt` — JVM 13건. 상향/하향/유지, 저장 폭주로 인한 하향, ±1단계 제한, 변경 후 대기, 세션 부족, 최신 3개만 반영, 빈 퀴즈 창, 경계 clamp, 저장된 값이 범위를 벗어난 경우.

### 연결한 것
- `LearningDao.listRecentSessions(limit)` — 최근 완료순. `@Query` 추가라 스키마 변경도 마이그레이션도 없다.
- `LearningRepository.listRecentSessionSummaries(limit)` — 엔티티를 `LearningSessionSummary` 로 바꿔 돌려준다. 도메인 정책이 Room 행 모양을 알 필요가 없다.
- `AppSettingsRepository` — `AppSettings.sessionsSinceDifficultyChange` 추가. `applyFinishedSession(decide)` 가 **하나의 `dataStore.edit` 안에서** 카운터 증가·난이도 갱신·변경 시 카운터 리셋을 함께 한다. 둘이 어긋나면 진동 방지가 무너지기 때문이다. 진단 저장은 카운터를 0으로 되돌린다. 난이도가 아직 없으면(진단 전) 아무것도 하지 않는다.
- `ResultRoute` 에 `onSessionRecorded: suspend () -> Unit` 훅을 넣었다. 기존 `hasRecorded` + `NonCancellable` 가드 **안**, 세션 행이 들어간 직후에 실행된다. 세션 기록과 정확히 같은 횟수로 실행되어야 하는 일이기 때문이다. 난이도 계산을 `ResultRoute` 안에 넣지 않은 것은 이 화면의 역할(세션 저장 + 스트릭)을 유지하고 설정 저장소 없이도 테스트할 수 있게 하기 위해서다.
- `LearningSessionRoute`, `HomeRoute` 는 훅을 그대로 넘긴다. 중간 계층은 DataStore 를 모른다.
- `EnglishQuizApp.adjustDifficulty()` 가 Room 과 DataStore 를 모두 아는 유일한 지점이다. 여기서 실패해도 삼킨다. 세션은 이미 기록됐고 그게 지켜져야 할 것이다. 난이도는 다음 세션에 다시 시도한다.
- `AppSettingsRepositoryTest` 에 3건 추가: 진단이 창을 초기화하는지, 세션이 카운트되고 변경 시 리셋되는지, 진단 전 세션이 난이도를 만들어내지 않는지.

### 최신 난이도가 생성 요청에 전달되는 경로
`AppSettingsRepository.settings` Flow → `EnglishQuizApp` → `LearningHome(difficulty=…)` → `LearningSessionRoute(difficulty=…)` → `ContentGenerationRequest(difficulty=…)` → Edge Function. 이 통로는 006 준비 코드에 이미 있었고 이번에 새로 만들지 않았다.

## 2026-09-22 적대적 리뷰 반영

### 고친 것
- **[높음] 새 DataStore 테스트 3건이 같은 파일을 썼다.** 파일명 문자열에 `$` 이스케이프가 잘못 들어가 `test-app-settings-${files.size}...` 가 리터럴로 박혔다. 기기에서 돌렸다면 `There are multiple DataStores active for the same file` 로 2건이 실패했을 것이고, "카운터와 난이도가 한 edit 안에서 원자적"이라는 013 의 핵심 근거가 증명되지 않은 상태였다. 같은 모듈의 `AssessmentFlowTest` 패턴(`System.nanoTime()` 고유 파일명 + 취소 가능한 `SupervisorJob`, `@After` 에서 취소·삭제)으로 다시 썼다.
- **[중간] `onSessionRecorded` 가 멱등하지 않았다.** `withContext(NonCancellable)` 블록은 끝까지 실행되지만, 블록이 끝나고 바깥 코루틴이 재개될 때 부모 Job 의 취소가 확인되면 `hasRecorded = true` 가 실행되지 않는다. 세션 행은 (learningDate, completedAtEpochMillis) 로 멱등이라 안전했지만 난이도 카운터는 아니었다. 실제 세션 2회만에 카운터가 3에 도달하면 창은 열리는데 그 창에는 직전 난이도 변경 *이전* 세션이 섞여 들어간다 — 진동 방지가 뚫리는, 정확히 막으려던 시나리오다. 훅이 세션의 `completedAtEpochMillis` 를 받고, `applyFinishedSession` 이 같은 값이면 건너뛴다. 식별자도 같은 `edit` 안에 저장해 원자성을 유지한다.
- **[중간] 경계값이 테스트로 고정되어 있지 않았다.** 13건 모두 경계에서 떨어진 값만 써서, 네 비교 연산자 중 어느 것을 뒤집어도 전부 통과했다. `done_when` 의 "상·하향 경계가 테스트 가능할 것"을 충족하지 못한 상태였다. 정확히 85%(17/20), 정확히 50%(15/30), 평균 저장 정확히 2.0, 정확히 12.0 과 그 바로 바깥값까지 8건을 추가해 네 경계를 양쪽으로 고정했다.
- **[낮음-중간] 퀴즈 하루가 창 전체를 결정할 수 있었다.** `[퀴즈 10/10·저장 6], [퀴즈 없음·저장 0], [퀴즈 없음·저장 0]` 이면 정답률 100%, 평균 저장 2.0 으로 상향되는데, 실제로는 퀴즈를 한 번 봤고 거기서 모르는 표현이 6개 나온 학습자다. 상향 후 다음 창에서 되돌아올 가능성이 높아 6세션 주기 진동이 된다. `MIN_SESSIONS_WITH_QUIZ = 2` 를 넣어 창의 최소 2세션이 실제로 퀴즈를 본 경우에만 판단한다.

### 리뷰가 확인해 문제없던 것
- `?: return@edit` 는 편집 취소가 아니라 "변경 없음"이고, DataStore 는 값이 같으면 디스크 쓰기를 건너뛴다. 손상이나 빈 커밋 없음.
- `LearningDao` 의 `@Query` 추가는 스키마·엔티티·버전(3)을 바꾸지 않아 마이그레이션 영향이 없다. `ORDER BY completedAtEpochMillis DESC, id DESC` 는 동시각 세션에도 결정적이다.
- 최신 난이도가 `ContentGenerationRequest` 까지 전달된다. `LaunchedEffect(retry)` 가 difficulty 를 키로 쓰지 않아 세션 중 난이도가 바뀌어도 진행 중 세션이 리셋되지 않는다.
- 정수 나눗셈 절삭은 경계를 잘못된 방향으로 넘기지 않는다.

### 남겨 둔 판단
`aSessionBeforeAnyDiagnosisLeavesTheLevelUnset` 이 검증하는 상태(난이도 미설정 + 세션 종료)는 `saveAssessmentResult` 가 두 값을 한 edit 에 쓰므로 현재 도달 불가능하다. 방어 분기와 테스트를 남긴다. 그 상태가 어떤 경로로든 생기면 UI 는 `DEFAULT_DIFFICULTY=2` 로 학습을 계속하면서 난이도는 영영 조절되지 않는 조용한 고착이 되는데, 난이도를 여기서 임의로 만들어 진단 결과를 덮어쓰는 것보다는 낫다고 판단했다.
