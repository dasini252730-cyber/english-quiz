## 목적

3. **출제 불가 표현 처리**: 보기를 2개 이상 만들 수 없는 표현은 대체 보기(지문의 짧은 뜻끼리 활용)를 시도하거나 "출제 불가" 상태로 분리 (백로그 057과 함께 처리)

## 결정과 검증 기록 (2026-10-14, 메인 에이전트)
- `kind`는 사전 품사가 아니라 문장에서 채우는 자리로 정의했다: noun / verb(구동사·동사 관용구 포함) / adjective(under the weather 같은 서술 관용구 포함) / adverb / remark(no way 같은 고정 대사). 스키마 enum으로 강제하고, 목록 밖 값은 서버·앱 모두 ""로 떨어뜨려 지문을 버리지 않는다.
- 보기 후보는 같은 kind를 먼저, kind 미상(옛 표현)을 그다음에 쓰고, 다른 kind는 쓰지 않는다. 처음엔 다른 kind를 마지막 단계로 두었으나 리뷰(code-critic)가 "명사 셋 사이의 동사 하나"처럼 뜻을 몰라도 정답이 보이는 최악 사례가 바로 사용자 불만이라고 지적해 제거했다. 보기가 모자라면 2지선다로 줄고, 하나도 없으면 null(복습함 "출제 불가", 057). 정답 kind가 ""이면 전원이 한 단계.
- 리뷰 반영 2: 지문 표현이 뜻 고르기 보기로 들어오면서 정답의 굴절형("pulled it off")이 오답으로 나올 수 있어, 오답 후보는 `typedAnswerMatches`(축약·앞의 to·머리말 굴절 관대 비교)로 정답과 같은 표현이면 제외한다. 저장 경계(`LearningRepository`)에서도 kind를 `ExpressionKinds.normalize`로 한 번 거른다. 모델이 한 번 잘못 붙인 kind는 짧은 뜻과 같이 바꾸지 않는다(빈 값만 채움).
- 대체 보기: 뜻 고르기에서 짧은 뜻은 저장 표현뿐 아니라 오늘 지문의 표현에서도 가져온다(짧은 뜻끼리라 길이로 답이 드러나지 않음). 긴 뜻은 여전히 저장 표현에서만. 둘 중 보기 수가 더 많은 쪽을 쓴다. `isAskable()`은 복습함만 보므로 복습함 "출제 불가" 표시는 그대로다.
- 옛 저장 표현은 마이그레이션(Room v11)으로 kind ""를 받고, 같은 표현이 나중 지문에 다시 나오면 `fillKind`로 한 번 채운다(짧은 뜻과 같은 규칙).
- 보기 생성 로직은 `QuizOptions.kt`로 분리했다(QuizBuilder 228→158줄).
- 리뷰 반영 3(후속 리뷰): 지문 이해 문제(042)의 보기도 세션 Random으로 섞는다(모델이 정답을 특정 번호에 두는 경향 → 사용자가 본 "정답 번호 쏠림"의 유력한 원인). 불규칙 과거형(took/made/went 등 약 70개 동사)을 `stem()` 앞에서 원형으로 접어 오답 후보 제외와 직접 입력 채점(058) 양쪽에 같이 적용한다. 저장 경계 테스트(`LearningRepositoryKindTest`: 목록 밖 kind는 "", 빈 kind만 백필, 기존 kind는 덮어쓰지 않음)와 옛 표현(kind "")↔새 표현 양방향 호환 테스트를 추가했다. 세션 내 정답 위치 검증은 20세션×10문항 합산으로 각 칸 30회 이상. `retrySaveMeaning`은 기존처럼 짧은 뜻·kind 없이 저장하고 다음 지문/탭에서 채운다(변경 없음). 단어 하나짜리 표현의 과대 축약(care/car)은 안전한 방향(중복 보기 방지)이라 그대로 둔다.
- 검증: Edge Function 테스트 31개 통과, 단위 테스트 156개 통과(새 `QuizKindOptionsTest` 7개 포함: 같은 kind 우선, 미상 kind 허용, 다른 kind는 절대 제시 안 함(축소/출제 불가), 정답 굴절형 제외, 같은 kind 지문 짧은 뜻 대체 보기, 세션 간 200회 시드에서 정답 위치 4곳 모두 25회 이상, 한 세션 10문항 안에서 위치 3곳 이상), lintDebug 오류 0, assembleDebug 성공.
