# 006 AI 콘텐츠 생성 연동

## 목적
Conversation 또는 Story 선택 시 저장된 복습 표현과 현재 난이도를 반영한 학습 콘텐츠를 생성한다.

## 작업 범위
- 선택 모드, 현재 난이도, 복습 대상 표현을 생성 요청에 전달한다.
- 복습 표현과 신규 표현을 섞고, 부족한 초기 기록에서는 신규 표현 중심으로 만든다.
- 약 10분 학습 분량의 맥락이 이어지는 대화/성인용 짧은 이야기를 만든다.
- 화자/문장/표현 위치와 필요한 표현 메타데이터를 구조화해 Reader에서 쓸 수 있게 한다.
- 로딩, 실패, 다시 시도 상태를 제공한다.

## 완료 기준
- 두 모드의 응답이 파싱 가능한 콘텐츠 모델로 변환된다.
- AI 호출 키는 앱에 포함되지 않는다.
- 시간 초과/잘못된 응답에서 앱이 중단되지 않고 재시도 안내가 나온다.

## 확정된 제품·기술 결정
- Provider는 OpenAI API 하나만 사용한다. MVP 기본 모델은 `gpt-5.6-terra`로 둔다. 사용자가 학습 품질을 비용 최적화보다 우선한다고 결정했으며, Luna로 바꾸고 싶을 때는 Edge Function의 설정값만 바꾼다.
- Android 앱은 Supabase Edge Function에 최소 요청(모드, 현재 난이도, 필요한 복습 표현)을 보내고, Edge Function이 OpenAI Responses API를 호출한다. 함수의 `OPENAI_MODEL` 환경 설정 기본값은 `gpt-5.6-terra`다.
- OpenAI API key는 Edge Function secret에서만 읽는다. APK, BuildConfig, local.properties, 클라이언트 설정에는 두지 않는다. Auth나 회원 체계는 추가하지 않는다.
- Edge Function은 요청을 검증하고 상한이 있는 timeout, 비정상 요청 방어, 명확한 비성공 응답을 제공한다. Android는 timeout/전송 실패/잘못된 구조 응답에서 생성물로 오인하지 않고 재시도 안내를 보여준다.
- OpenAI 응답은 Reader가 파싱하는 구조화 JSON으로 제한한다. Conversation, Story, 문맥 뜻 생성에 사용한다. 이번 작업의 JSON schema 계약은 실제 Reader 모델에 맞춰 구현 시 확정하고 테스트한다.
- 생성 콘텐츠를 Supabase나 별도 서버 DB에 저장하지 않는다. Edge Function/OpenAI 응답을 Android로 반환하고, 저장이 필요한 학습 상태만 기존 Room 저장소에 기록한다. OpenAI Responses 요청은 애플리케이션 응답 상태 저장을 끄는 옵션을 사용한다. 이 설정만으로 제공자 측 abuse-monitoring 보존까지 없어진다고 가정하지 않는다.
- MVP에서는 요청량 최적화를 우선하지 않는다. 응답 길이와 기본 입력 검증은 비정상 요청 방지에 필요한 수준으로 제한하고, 실제 사용량을 관찰한 뒤 비용 조정을 별도 결정한다.

## 구현 시 확인할 자료와 순서
1. `app/src/main/kotlin/com/englishquiz/app/data/local/` 및 `data/repository/`에서 콘텐츠와 로컬 학습 기록의 실제 모델/API를 확인한다. Task 002의 계측 저장·복원 gate가 풀리기 전에는 이 연동을 완료로 판정하지 않는다.
2. Supabase Edge Function의 요청/응답 계약과 검증을 작성한다. 생성 응답에는 필요한 콘텐츠 필드만 반환하고 서버 DB, 대화 로그, 학습 이력 저장을 추가하지 않는다.
3. OpenAI Responses API의 strict JSON schema 출력으로 모델 응답을 제한하고, 모델명은 `OPENAI_MODEL` 환경변수에서 읽는다. 기본값은 `gpt-5.6-terra`다.
4. API key 누락, 잘못된 입력, 제공자 오류/timeout, 구조화 응답 해석 실패를 각기 앱에 안전하게 전달하고 다시 시도할 수 있도록 처리한다. 중복 자동 재시도는 과금할 수 있으므로 사용자가 다시 시도하는 흐름으로 둔다.
5. 요청 검증, 응답 parsing, timeout/error 경로를 테스트한다. Supabase 로컬 실행 도구가 없는 환경에서는 Edge Function 테스트/배포를 완료했다고 주장하지 않는다.

## 2026-09-24 크레딧 충전 후 실호출 검증과 수정

사용자가 Anthropic 크레딧을 충전했다. `meaning` 은 바로 200 이 됐지만 `content` 는 두 모드 모두 502
`provider_request_rejected`(제공자 HTTP 400) 였다. 아래 두 결함을 찾아 고쳤고, 최종적으로 두 모드 ×
난이도 3단계 12회 호출이 전부 성공했다.

### 결함 1 — 스키마에 Anthropic 이 거부하는 키워드가 있었다
`CONTENT_SCHEMA` 의 `minItems`/`maxItems` 가 원인이다. Anthropic structured outputs 는 배열 길이
제약을 지원하지 않아 요청 전체가 400 이 된다. 제약이 없는 `MEANING_SCHEMA` 만 동작한 이유가 이것이다.
공식 SDK 는 미지원 키워드를 자동으로 떼고 보내지만 이 함수는 raw `fetch` 를 쓰므로 그 보정을 못 받는다.

- 스키마에서 두 키워드를 제거했다. 8..40 세그먼트 / 1..40 표현 경계는 원래부터 `validateModelOutput`
  이 강제하고 system prompt 에도 명시돼 있어 계약 손실은 없다.
- `index.test.mjs` 에 `assertOnlySupportedKeywords` 를 넣어 두 스키마를 모두 검사한다. 미지원 키워드
  23종(배열/수치/문자열/객체 제약, `oneOf`, `not`, `if`/`then`/`else` 등)을 막고, JSON Schema 가 실제로
  하위 스키마를 중첩하는 위치만 내려간다 — `properties` 맵까지 훑으면 나중에 `pattern` 같은 이름의
  도메인 필드가 생겼을 때 정상 스키마를 오탐한다. 키워드를 되살려 테스트가 실제로 실패하는 것을 확인했다.

### 결함 2 — 표현 하나가 안 맞으면 지문 전체를 버렸다
수정 1 이후에도 난이도 1 에서 8회 중 3회가 502 였다. 원인을 추측하지 않으려고 응답에 `error.check`
필드를 추가해(우리 계약 이름 화이트리스트만 노출, 내부 메시지는 `unknown` 으로 마스킹) 실패 항목을
직접 관측했고 전부 `expression_not_in_segment` 였다. 성공한 실행의 세그먼트 수가 16·21·25 였으므로
세그먼트 하한(8)은 원인이 아니었다.

- 모델이 굴절형("pulled it off")이나 다른 활자 부호를 쓰면 표현이 세그먼트 본문에 그대로 없고, 그러면
  신뢰할 수 있는 offset 이 없다. 이제 그 표현 하나만 버리고 나머지 지문은 살린다. 20개 세그먼트를
  표현 하나 때문에 버리는 것이 더 나쁘다. 반드시 남아야 하는 것(요청한 복습 표현 전부, 신규 표현 최소
  하나)은 기존 검증이 그대로 강제하므로 계약은 유지된다.
- 활자 부호 차이는 `foldTypography` 로 흡수한다. curly apostrophe·smart quote·NBSP·dash 변형을 ASCII 로
  접되 **한 글자 → 한 글자** 로만 매핑한다. offset 이 Reader 의 하이라이트 좌표라 길이가 바뀌면 엉뚱한
  단어에 밑줄이 그어지기 때문이다.
- 같은 규칙을 Android `AiLearningResponses.kt` 에도 넣었다. 앱이 서버보다 엄격하면 서버가 통과시킨
  응답을 앱이 `invalid_response` 로 되던진다. 두 구현은 서로를 주석으로 가리킨다.

측정: 수정 전 난이도 1 에서 8회 중 3회 실패 → 수정 후 story/conversation × 난이도 1·2·3 각 2회, **12/12 성공**.

### 함께 고친 것
- `REQUEST_TIMEOUT_MS` 25s → 60s. story 한 번이 25s 를 넘겼다. 성공 실행은 9~21s 다. Android
  `readTimeoutMillis` 는 30s → 75s 로 올려 함수의 오류 코드가 소켓 타임아웃보다 먼저 도착하게 했다.
- 그 결과 죽은 분기가 될 뻔한 timeout 안내를 살렸다. `LearningSessionRoute.generationErrorMessage` 가
  함수의 `provider_timeout` 도 timeout 문구로 매핑한다.
- `AiLearningClient` 의 취소 경쟁을 좁혔다. `disconnect()` 는 요청이 시작되기 전에는 no-op 이라,
  연결 생성 직전에 도착한 취소는 워커를 끝까지 돌게 뒀다. read timeout 이 75s 가 되면서 최악 대기가
  길어지므로 취소 플래그를 두어 워커가 스트림을 열기 전에 스스로 멈춘다.
- 파싱을 `AiLearningResponses.kt` 로 분리했다. 순수 함수가 되어 소켓 없이 실제 페이로드로 검증할 수 있다.

### 실기기(에뮬레이터) 전 구간 확인
`-PaiEndpoint=...` 로 빌드해 에뮬레이터에 설치하고 진단 8문항 → 홈 → Conversation 을 실제로 통과시켰다.
Reader 에 화자 구분된 실제 대화가 표시됐다. 즉 앱 → Edge Function → Anthropic → 구조화 JSON →
Android 파서 → Reader 경로가 실호출로 동작한다.

### 테스트
- Edge Function 핸들러 테스트 9건 통과(기존 6 + 스키마 가드 확장, 드롭 동작, 활자 부호 정합, `check` 노출).
- Android 계측 `AiLearningResponsesTest` 8건 신설. 배포된 함수에서 **실제로 받은 페이로드**(`app/src/androidTest/assets/ai/`)
  로 두 모드가 콘텐츠 모델로 변환되는지, 표현 offset 이 자기 단어에 정확히 떨어지는지, 요청한 복습 표현이
  주석돼 오는지, 다른 모드·깨진 offset·`data` 없는 응답이 거절되는지를 검증한다. 손으로 쓴 fixture 는
  파서가 자기 자신과 일치하는 것만 증명하므로 쓰지 않았다.

### done_when 대조
- **두 모드의 응답이 파싱 가능한 콘텐츠 모델로 변환된다** — 충족. 실호출 12/12 성공, Android 파서가 실제
  페이로드로 검증됨(계측 8건), 에뮬레이터에서 Reader 까지 표시 확인.
- **AI 호출 키는 앱에 포함되지 않는다** — 충족. 키는 Supabase secret 에만 있고 `x-api-key` 헤더로만
  나간다. APK 에는 엔드포인트 URL 만 들어간다(`aiEndpoint` Gradle property, query string 금지 검증).
  핸들러 테스트가 요청 본문·응답 어디에도 키가 없음을 단언한다.
- **시간 초과/잘못된 응답에서 앱이 중단되지 않고 재시도 안내가 나온다** — 충족. 함수가 제공자 실패를
  `provider_auth`/`provider_model_unavailable`/`provider_request_rejected`/`provider_busy`/`provider_timeout`
  로 나누고 제공자 본문은 절대 전달하지 않는다. 앱은 timeout·network·invalid_response·provider_busy 에
  각각 다른 안내를 주고 나머지는 일반 재시도 안내로 떨어진다. Reader/세션 양쪽에 재시도 버튼이 있다.

선행 002·005 가 모두 `done` 이고 완료 기준 증거가 확보되어 `done` 으로 옮긴다.

## 2026-09-24 2차 적대적 리뷰 반영
- **스키마 회귀 가드가 `MEANING_SCHEMA` 를 검사하지 않았다.** 뜻 조회는 요구사항 11절의 진입점이라
  같은 사고가 나면 타격이 더 크다. meaning 테스트도 요청 본문을 캡처해 같은 단언을 건다.
- **미지원 키워드 목록을 23종으로 넓혔다**(`exclusiveMinimum`/`exclusiveMaximum`/`minProperties`/
  `maxProperties`/`oneOf`/`not`/`if`/`then`/`else`/`contains`/`prefixItems`/`patternProperties`/
  `propertyNames` 추가). 또 JSON Schema 가 실제로 하위 스키마를 중첩하는 위치만 내려간다 — `properties`
  맵까지 훑으면 나중에 `pattern` 같은 이름의 도메인 필드가 정상인데 오탐된다.
- **fold 매핑이 보이지 않는 문자 리터럴로 들어가 있었다.** 편집기나 패치 도구가 하나만 정규화해도 앱이
  서버보다 엄격해지는데 실패하는 테스트가 없다. 양쪽 모두 `\uXXXX` 이스케이프로 바꾸고, 14개 코드포인트
  전부를 표로 검증하는 테스트를 Kotlin·TypeScript 양쪽에 추가했다.
- **길이 불변식을 가드로 고정했다.** 소문자화는 길이를 바꿀 수 있고(U+0130) 그러면 offset 이 밀린다.
  서버는 그런 표현을 버리고 앱은 거절한다. 양쪽에 테스트를 넣었다.
- **드롭이 완전히 조용했다.** 이 버그를 진단할 때 쓴 관측 수단이 정작 자기 실패 모드에는 없었다. 버린
  개수와 내용을 서버 로그에 남긴다(호출자에게는 노출하지 않음).
- `!data.has("title")` 중복 검사를 제거했다. 바로 다음 줄 `requiredString("title")` 이 이미 막는다.
