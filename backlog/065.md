## 작업 범위

### 1. Prompt Caching 구조 적용
- `prompts()` 함수 반환값: system을 문자열에서 배열로 변경
  - story 시스템: story_rules_v3.md 고정 부분 → cache_control ephemeral 적용
  - season 시스템: season_plan_rules.md 고정 부분 → cache_control ephemeral 적용
  - 가변 부분(난이도, SEASON_TOPIC 등)은 cache_control 없음
- `callProvider()` 함수: JSON 요청의 system 필드를 배열 형식으로 전송

### 2. SEASON_SCHEMA 확장
- `engine`: 문자열, "A" | "B" | "C" | "D" | "E" (season_plan_rules.md §1의 5가지 엔진)
- `whatIsTrue`: 배열, 문자열 항목들 (시즌의 사실, 비밀 포함)
- `readerBelieves`: 배열, 정확히 7개 문자열 (에피소드 1~7 후 독자가 믿는 것)
- SeasonBible과 SeasonCharacter의 relationships 필드는 유지

### 3. validateSeasonOutput에서 relationships 절단 제거
- 이전: `englishLine(person.relationships, 300)`으로 300자에서 잘라 반환했음 (반환 자체는 되고 있었음)
- 수정: `englishText()`로 평탄화·한글 검사만 하고 길이는 자르지 않음

### 4. story-rules.ts의 STORY_RULES 상수 업데이트
- story_rules_v3.md의 내용을 반영하도록 STORY_RULES 상수 재작성 (또는 파일 로드)

## 구현 기록 (2026-10-16)

### 결정 사항 (기술 기본값, 메인 에이전트)
- **system 블록 순서**: v3 머리말대로 규칙 블록이 먼저(캐시 접두), 난이도 루브릭·passage contract·회차 브리프는 둘째 블록. 028에서 "규칙이 먼저면 expressions를 비웠다"는 기록이 있었으나 v3 §9가 계약을 직접 언급하므로 규칙 우선을 따름. 재발하면 둘째 블록 맨 앞의 contract 문구를 강화.
- **캐시 TTL**: 기본 ephemeral(5분). 하루 한 번 호출되는 앱 특성상 실제 히트는 같은 호출의 재시도(CONTENT_ATTEMPTS=2)나 프리페치 직후 재호출에서만 발생. 1h TTL은 쓰기 비용이 2배라 보류.
- **시즌 설계 모델**: `season_plan_rules.md`는 Opus를 전제하지만 비용 결정이므로 기본값은 기존 `ANTHROPIC_MODEL`과 동일. `ANTHROPIC_SEASON_MODEL` 환경 변수로만 바꿀 수 있게 함(예: `claude-opus-5`). 바꾸려면 Supabase secret 설정 후 재배포.
- **새 필드의 회차 브리프 전달**: v3 §8이 engine·WHAT IS TRUE·reader-believes를 회차 호출의 입력으로 명시하고, 설계도는 한 번 저장되면 교체되지 않으므로 지금 저장하지 않으면 영구 손실. 그래서 SeasonBible 코덱·SeasonContext·SeasonCoordinator에 세 필드를 추가하고 서버 seasonContext/seasonClause가 선택적으로 받아 `<what_is_true>`/`<reader_believes>` 태그로 출력. 7편 plan 전체 전달은 16KB 본문 한도 때문에 하지 않음.
- **리스트 캡(리뷰 반영)**: 설계 저장은 20항목×400자. 회차 요청은 앱 `SeasonContext.toJson`이 12항목×300자로 잘라 보내고 서버 `seasonContext`도 같은 수치(MAX_BRIEF_*)로 읽음. 리스트가 커도 본문 한도를 넘어 시즌 전체가 413으로 멈추는 일이 없도록 함.
- **본문 한도**: 모든 필드가 상한에 닿은 story 요청은 약 19KB라 `MAX_BODY_BYTES`를 16KB→32KB로 올림(테스트도 32,769바이트로 갱신).
- **engine 값(리뷰 반영)**: 스키마 enum과 검증기가 다섯 엔진 문자열("A. Clever mystery" … "E. Predicament")만 허용. 다른 값은 `invalid_season_output(engine)`.
- **readerBelieves 번호(리뷰 반영)**: 서버 `seasonContext`는 줄을 위치별로 읽어 걸러진 줄(한글 등)은 빈 자리로 남기고, `seasonClause`는 빈 자리를 건너뛰며 원래 회차 번호로 표기. 걸러진 줄 때문에 4편 믿음이 3편으로 밀리는 일이 없음.
- **ANTHROPIC_SEASON_MODEL 테스트**: 설정 시 season 호출만 그 모델, 미설정 시 ANTHROPIC_MODEL을 쓰는 것을 테스트로 고정.
- **배포 순서(주의)**: dev에 push하면 GitHub Releases로 APK가 자동 배포되므로, **push 전에 `supabase functions deploy ai-learning`을 먼저** 해야 한다. 순서가 뒤집히면 함수 배포 전까지 새 시즌 생성(스토리 모드)이 실패한다. 서버 먼저, APK 다음. 새 APK는 `parseSeasonResponse`에서 engine과 readerBelieves 7줄이 없는 설계도를 거부하므로(한 번 저장되면 교체되지 않는 설계도가 빈 필드로 7편을 끌고 가지 않도록), 서버보다 APK가 먼저 나가면 새 시즌 생성이 서버 배포 전까지 `invalid_response`로 실패한다. 구 APK는 새 서버와 그대로 호환됨(모르는 필드 무시).

### 남은 절단 지점 (이번 범위 밖)
- 회차 브리프의 인물 줄은 여전히 `SeasonBible.castLine(2400)`이 인원수로 균등 분배해 자름(4명이면 1인 598자). 설계도에 저장된 relationships는 온전하지만 회차 프롬프트에는 잘려 들어갈 수 있음. 올리려면 MAX_CHARACTERS_CHARS·MAX_CAST_LINE·본문 한도를 함께 조정해야 함.
