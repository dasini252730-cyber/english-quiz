# 011 간격 반복 상태 계산

## 목적
퀴즈 답변을 결정적이고 테스트 가능한 규칙으로 표현 복습 상태에 반영한다. AI 호출이나 화면 의존 없이 계산하며 Room에 결과를 저장한다.

## 선행 작업 및 현재 제약
- 선행 작업 002는 현재 `in_progress`다. Room 스키마와 `LearningRepository.saveReviewProgress(...)` 연결은 존재하지만 완료로 확인되기 전까지 저장 계층이 바뀔 수 있음을 감안한다.
- `SavedExpressionEntity`에는 `lastReviewedAtEpochMillis`, `nextReviewAtEpochMillis`, `consecutiveCorrectCount`, `incorrectCount`, `isMastered` 필드가 있다. 순수 정책 계산을 위해 `ReviewProgress`가 이 값을 일시 투영하며, 별도 저장 모델이나 중복 DB 필드를 만들지 않는다. Entity와 투영 사이 매핑은 Repository 한 곳에 둔다.
- `LearningDao.findDueExpressions(nowEpochMillis)`는 아직 기한이 오지 않은 항목을 제외하고, `NULL` 및 `nextReviewAtEpochMillis <= nowEpochMillis`인 항목을 반환한다. 마스터 상태도 별도 제외하지 않아 30일 후 재등장한다.
- 현 저장소는 `minSdk 34`이며 복습 시각은 epoch milliseconds, 학습 일자는 `yyyy-MM-dd` 문자열이다. 이 작업의 간격 계산은 현지 날짜가 아닌 정확한 경과 시간을 기준으로 한다.
- 요구사항은 맞으면 간격 증가, 틀리면 간격 단축, 반복 정답 시 암기 완료, 완료 항목의 장기 복습 재등장만 규정한다. 구체 간격표, 완료 임계값, 완료 후 재등장 간격은 구현 시작 시 코드 상수와 문서/테스트로 명시할 MVP 정책이 필요하다. 기존 사용자 데이터에 영향을 줄 수 있으므로 계산 규칙 변경 시 마이그레이션 필요 여부도 검토한다.

## 선택한 MVP 정책
- `nextReviewAtEpochMillis == null`이면 즉시 복습 가능하다.
- 정답 간격은 연속 정답 횟수별로 1회 1일, 2회 3일, 3회 7일이다. 4회 연속 정답부터 마스터 상태로 표시하고 30일 간격을 유지한다.
- 오답은 연속 정답을 0으로, 마스터 상태를 해제하고 오답 횟수를 1 늘린 뒤 평가 시각으로부터 1일 후에 다시 복습한다.
- 모든 간격은 평가 시각(epoch milliseconds)에 정확한 24시간 배수를 더한다. 현지 날짜 및 DST 보정은 하지 않는다. `nextReviewAtEpochMillis <= nowEpochMillis`이면 기한 도래로 본다.

## 실무 작업 순서
1. 위 MVP 정책을 상태 전이 테스트로 고정한다: 연속 정답 1/2/3/4회, 마스터 유지, 마스터 항목 오답.
2. 결정적 복습 정책을 순수 Kotlin으로 구현한다. 현재 시간을 외부 입력으로 받아 시스템 시계를 내부에서 직접 읽지 않게 하며, 간격표와 암기 완료 임계값은 한 곳에서 관리한다.
3. 복습 기한은 epoch milliseconds를 기준으로 계산하며, 현지 시간대 변환이나 날짜 경계 처리를 추가하지 않는다.
4. `LearningDao`에 due 표현 쿼리를 추가하고 마스터 표현도 정해진 장기 복습일까지 다시 조회되는지 확인한다. 아직 기한이 오지 않은 표현과 `nextReviewAtEpochMillis == null`인 초기 표현의 처리도 명시한다.
5. 계산 결과를 기존 repository 저장 API에 연결한다. 표현 상태 읽기-계산-쓰기가 일관되게 처리되도록 트랜잭션 경계를 확인하고 이전 상태의 필드를 덮어쓰지 않도록 한다.
6. 단위 테스트로 상태 전이와 평가 시각 입력을 검증하고, Room 테스트로 결과 저장 및 기한 정각 전/정각/후 due 조회를 검증한다. 테스트는 각 `done_when`을 직접 증명해야 한다.
7. `gradlew.bat lint assembleDebug`와 관련 테스트를 실행한다. 환경상 검증할 수 없는 항목은 완료 처리하지 않고 blocker를 기록한다.

## 완료 기준을 검증 가능한 항목으로 풀이
- 같은 이전 상태, 같은 답변, 같은 평가 시각은 항상 같은 새 상태와 복습 시각을 반환한다.
- 정답/오답 및 연속 정답의 각 경계에서 정해진 간격표·카운터·암기 완료 기준이 테스트로 입증된다.
- 정확한 24시간 epoch 기반 간격 규칙과 `<= now` due 경계가 정의되고 Room 조회에서 정각 전/정각/후 테스트가 있다.
- Room에 저장된 상태를 다시 읽었을 때 계산 결과와 일치하며, due query는 기한 이전/정각/이후와 암기 완료 재등장 사례를 올바르게 구분한다.
- 계산 및 조회는 네트워크/AI에 의존하지 않는다.

## 현재 구현 및 검증 기록
- 순수 정책은 `ReviewProgress` 투영 값만 입력/출력하며, Repository가 Entity와 매핑한다. 답변 기록의 read-calculate-write는 Room transaction 안에서 수행한다.
- 정책 JVM 테스트는 통과했다. `:app:lint :app:assembleDebug :app:compileDebugAndroidTestKotlin`도 통과했고 Room 통합 테스트가 컴파일됐다.
- `ReviewProgressPersistenceTest`는 production DB가 아니라 계측 전용 고유 DB를 사용한다. 그러나 connected instrumentation에서 emulator의 target/test package dataDir가 생성되지 않고 Activity host도 resolve되지 않아 파일 Room persistence 및 due query를 실행하지 못했다.
- 리뷰어는 이 실행 실패를 emulator/test infrastructure 문제로 판정했고 별도 blocker `016`으로 분리했다. 따라서 이 작업은 `review_needed`이며, 정상 Android sandbox에서 마스터 상태 저장·재개방과 due query 경계를 검증하기 전에는 `done` 처리하지 않는다.
