# 075 시즌 생성 구조 재편: 백그라운드 설계도→회차 분할 호출, 회차별 저장·재시도, 준비 중 화면, 대화를 같은 회차 호출로 통합(companion 경로 제거), 캐시 블록 정렬

## 목적
2026-10-18 사용자 지침 1부. (트리거) 시즌 생성은 탭에서 시작하지 않는다. 첫 시즌은 진단 시작 시, 다음 시즌은 현재 시즌 회차가 모두 생성된 뒤 안 읽은 회차가 2개 이하로 떨어지는 순간(회차 읽음 처리 시점) 백그라운드에서 시작. 결과 화면의 선생성 트리거(ContentPrefetcher)는 제거. 안 읽은 회차가 없을 때 탭하면 '준비 중이에요'와 '지난 회차 다시 읽기'를 보이고 준비되면 홈이 자동 갱신. (분할) 설계도(ANTHROPIC_SEASON_MODEL=Opus) → 회차 호출. 0부 측정(Haiku 출력 ~92 tok/s, 지문 평균 3,060·최대 5,353 토큰, 함수 상한 150s)에 따라 회차 호출은 한 번에 1편(스토리+대화 ≈ 6,100 평균·최대 ≈ 9,000 토큰 ≈ 100s)으로 나누고 max_tokens 11,000·서버 타임아웃 130s·앱 읽기 타임아웃 145s. 1편이 저장되는 즉시 홈에서 열 수 있어야 하며 2~7편은 순차 백그라운드. 편별 저장, 실패한 편만 재시도. (대화 통합) 회차 호출 스키마 episodes[]의 각 항목에 story와 conversation. system = [story rules][Conversation Rules][레벨 rubric](캐시) → [시즌 브리프](캐시) → [앞 편 본문][이번 편 plan]; user에는 상황 23개 목록과 회차 범위만. 대화 검증은 기존 계약, 대화만 위반이면 스토리는 저장하고 대화만 재요청(스토리 본문을 넘기는 conversation-only 호출; 기존 안 읽은 레거시 회차의 대화도 이 경로로 생성). 저장은 (시즌, 회차, mode) 키. companionFor·companionForNextRead·PassageSummary·서버 passageSummary()·<companion> 프롬프트 제거. 홈의 대화 N은 스토리 N과 같은 회차, 어느 쪽을 먼저 열어도 같다. 날짜가 지난 미열람 대화(daily_content 미래 날짜 행)는 버린다. 영어·중국어 호출 모두 규칙 블록 적용, 언어 고정 표현은 요청 언어로 치환. (테스트) 서버: 대화 N 입력에 스토리 N 세그먼트 포함 / 대화 N 화자가 스토리 N 등장인물에 포함 / 호출별 예상 출력 토큰·시간이 상한 이하. 앱: 안 읽은 2개에서 다음 시즌 생성 시작 / 0개면 준비 중 화면과 백그라운드 생성 / 대화 먼저 열어도 같은 회차. 끝나면 companion grep 결과와 1편 호출 프롬프트 덤프 갱신.

## 결정 기록 (2026-10-18, 기술 기본값)

- 호출 분할: 0부 측정(출력 ~92 tok/s, 지문 최대 5,353 토큰, 무료 플랜 150s)으로 한 호출에 1편(스토리+대화). `episodes.ts`의 EPISODES_PER_CALL은 측정 상수에서 계산되며 서버 테스트가 상한 일관성을 검사한다. 사용자 제안(1→2~3→4~7편)은 2편부터 상한 초과.
- 서버 타임아웃 130s, max_tokens 11,000(대화만 6,000), 앱 읽기 타임아웃 145s. 설계도도 130s.
- 설계도 모델: ANTHROPIC_SEASON_MODEL=claude-opus-5 (사용자 지시 "설계도(Opus)"). Opus 5는 기본 thinking이므로 effort low, max_tokens 16,000.
- 캐시: Haiku 4.5 최소 4,096 토큰. 고정 블록(규칙+대화 규칙+두 지문의 계약·레벨)과 시즌 브리프 블록 두 곳에 캐시 표시. 계약을 고정 블록에 두고 회차 블록에는 표현 개수만 적는다.
- 회차 소비 단위: 스토리/대화 중 어느 쪽을 먼저 열어도 그 회차의 readDate가 기록되고 두 지문이 그날의 지문이 된다. 대화만 하고 스토리를 건너뛰면 그 스토리는 라이브러리에서 읽는다.
- 레거시 미열람 회차(대화 없음)는 삭제하지 않고 conversation-only 호출로 대화를 채운다. 미래 날짜의 daily_content 행만 마이그레이션에서 삭제.
- 첫 시즌 설계도는 진단 시작 시 레벨 3(기본값)으로 만들고, 회차는 생성 시점의 저장 레벨을 쓴다. 미리 만들어진 회차에는 레벨 변경이 적용되지 않는다(063 안내 유지).
- 복습 표현: 생성 시점 기준 7일 내 due 표현 최대 12개.
- 실패 정책: 한 단계 실패 시 해당 run 중단, 60초 뒤 ensure()에서 같은 단계부터 재시도. 호출 안 재시도 없음.
- 대화 화자 검증: 대화 화자 ⊆ 스토리 화자(Narrator 제외) ∪ 시즌 캐스트 이름. 위반 시 스토리만 저장하고 conversation-only로 재요청.

## WorkManager 이전 (2026-10-20, 사용자 지시)

- 파이프라인 실행을 WorkManager 체인으로 옮김. `SeasonPipeline.step(language)`가 단계 하나를 하고, `SeasonWorker`가 그 단계를 Worker 하나로 실행하며 다음 단계를 같은 고유 체인(`season-<lang>`)에 APPEND한다. 할 일이 없으면 체인 종료.
- 제약: NetworkType.CONNECTED, expedited(쿼터 없으면 일반 작업). 재시도: 지수 백오프 30초, 단계당 최대 5회(그 뒤 실패; 홈을 열면 새 체인). 200초 워치독은 제거하고 WorkManager의 작업 중단(10분)에 맡김.
- `SeasonScheduler.ensure`(KEEP)·`retryNow`(실행 중이 아니면 REPLACE). 앱이 열려 있을 때의 진행 상태는 `SeasonPipeline.status`로 준비 중 화면에 표시(같은 프로세스에서 Worker가 돌기 때문).
- 테스트: `SeasonWorkerTest`(WorkManagerTestInitHelper + TestListenableWorkerBuilder: 단계당 1 Worker, 다음 단계 APPEND, 실패 시 retry, 마지막 시도 후 failure), `SeasonPipelineTest.oneStepDoesOnePieceOfWork…`.
- 실기 확인 절차: 안 읽은 회차가 2개가 될 때까지 읽기 → 홈으로 나와 다음 시즌 체인이 시작되면 앱을 최근 앱에서 종료 → 10분 뒤 재실행 → 홈 카드의 "준비된 회차 N편"이 2+7=9편(또는 새 시즌 포함 증가)인지 확인. adb로는 `adb shell dumpsys jobscheduler | grep -A3 season` 또는 DB의 season_episodes 행 수.
